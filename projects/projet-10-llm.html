Projet 10

Assistant SportSee : évaluation et amélioration d’un système LLM

Un projet centré sur l’évaluation raisonnée, l’architecture hybride RAG + SQL et l’amélioration mesurable d’un assistant d’analyses sportives.

Le projet en bref

Ce projet vise à concevoir, analyser, améliorer et évaluer un assistant NBA capable de répondre à des questions de nature différente : questions documentaires fondées sur des contenus textuels, et questions statistiques fondées sur des données tabulaires structurées.

L’enjeu principal n’était pas seulement de produire une application fonctionnelle, mais de construire un système plus robuste, traçable et mesurable qu’un simple chatbot génératif.

La problématique

Une architecture RAG classique fonctionne relativement bien pour retrouver et synthétiser des contenus narratifs. En revanche, elle devient vite fragile lorsqu’une question nécessite un tri, une comparaison, un classement, un filtrage ou une agrégation précise sur des données tabulaires.

La problématique du projet a donc été la suivante : comment construire un assistant LLM capable de répondre à la fois à des questions documentaires et à des questions statistiques, tout en gardant un niveau minimal de robustesse, de traçabilité et d’évaluabilité ?

La démarche retenue

J’ai volontairement adopté une logique progressive : partir d’un système RAG initial, mettre en place une évaluation formelle, diagnostiquer les limites, puis faire évoluer l’architecture à partir de ce diagnostic.

Le projet suit donc une vraie chaîne d’amélioration continue : baseline → analyse → amélioration → réévaluation.

Logique du projet : ne pas corriger le système “à l’intuition”, mais appuyer les choix d’architecture sur des observations, des métriques et un diagnostic explicite.

Architecture finale

  • Streamlit pour l’interface utilisateur ;
  • Mistral + FAISS pour la branche RAG documentaire ;
  • SQLite pour les statistiques NBA structurées ;
  • Pydantic + PydanticAI pour structurer les données et centraliser le routage ;
  • SQL tool pour interroger les tables de manière contrôlée ;
  • RAGAS pour l’évaluation ;
  • Logfire + Docker + GitHub Actions pour l’observabilité et l’industrialisation minimale.

Pourquoi le système a évolué

La V1 traitait presque toutes les questions selon une logique linéaire retrieval → génération, en ramenant même les statistiques tabulaires à du texte. Cela rendait difficile l’analyse des erreurs et fragilisait les réponses sur les questions numériques ou comparatives.

L’introduction de PydanticAI et du SQL tool a permis de passer d’un pipeline fixe à un agent outillé capable de choisir dynamiquement le bon traitement selon le type de question.

Ce que j’ai amélioré

  • mise en place d’un runner d’évaluation formelle ;
  • ajout de métriques RAGAS et de métriques de retrieval ;
  • formalisation des objets de données avec Pydantic ;
  • introduction d’un agent PydanticAI ;
  • ingestion de l’Excel NBA dans une base SQLite ;
  • création d’un SQL tool avec garde-fous et refus hors périmètre ;
  • amélioration du retrieval documentaire via réécriture de requêtes, reranking et chunking différencié ;
  • réévaluation complète du système final.

Résultats marquants

Le projet a permis d’obtenir une amélioration très nette sur les métriques de génération les plus importantes.

  • Faithfulness : 0.530 → 0.954
  • Answer relevancy : 0.519 → 0.817
  • Tool routing OK : 0.956 sur le système hybride
  • Tool call F1 : 0.985

Les gains les plus nets concernent les questions numériques, désormais traitées à partir de données vérifiables via SQL plutôt qu’à partir d’une simple similarité textuelle.

Ce que ce projet montre

  • ma capacité à auditer un système LLM existant ;
  • ma capacité à distinguer les causes d’erreur au lieu de corriger “à l’intuition” ;
  • ma capacité à concevoir une architecture hybride adaptée à différents types de données ;
  • ma capacité à relier amélioration technique et évaluation mesurable ;
  • ma capacité à aller jusqu’à l’industrialisation minimale d’un prototype IA.

  • articulation entre preuve documentaire, preuve SQL et génération finale.

Limites assumées

Le projet reste dépendant de la qualité du dataset d’évaluation, du périmètre réel de la base locale et de certaines dépendances externes comme l’API Mistral pour certains tests d’intégration.

Les questions hybrides ou ambiguës restent aussi les plus difficiles, notamment lorsqu’elles mobilisent à la fois une dimension statistique et une dimension argumentative.

Statut du projet

Le projet est réalisé sous la forme d’un assistant hybride fonctionnel, évalué, amélioré puis réévalué, avec une logique d’industrialisation minimale.
